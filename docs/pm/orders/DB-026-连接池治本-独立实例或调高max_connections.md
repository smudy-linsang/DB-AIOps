# DB-026：连接池治本——独立实例或调高 max_connections

执行：MMMan

## 背景

- DB-005R 回执 §20（2026-11-13 上午实测）：宿主 08:35:54 重启后，时序库 `db-aiops-timescaledb`（`max_connections` 默认 100）被 DB_Monitor 开发实例（`manage.py runserver --noreload 0.0.0.0:8000`，宿主 PID 21728，经 Antigravity IDE language server 由 WSL 启动）占满 100/100，采集器、平台与 psql 一律被拒「too many clients」；采集守护与 Web 守护同型跨日缺陷（`pending_until` 仅存 `HH:MM:SS`）已于装置层修正；10:26–10:32 连接池释放、采集器（pid 48396）与 Web（pid 45704，health 200）恢复，今日 15:05/15:35/16:05 三轮前提已恢复、待实跑验证。
- 残余风险：DB_Monitor 开发实例已于 10:26:54/55 重启，占满连接池的成因仍在，若再次并发压满则采集器与平台将再度被拒。
- 用户 2026-11-13 拍板：三选一选治本（独立实例或调高 max_connections）。

## 任务

1. **评估两条治本路径，给出推荐**：(a) 为 DB-AIOps 分配独立 Postgres 实例（时序库与 DB_Monitor 开发实例彻底隔离）；(b) 调高时序库 `max_connections`，并给 DB_Monitor 侧设连接池上限。结合宿主资源、现有容器编排方式、数据迁移量与中断面，写明各路径的改动点、风险与回退办法，给出推荐路径与理由。推荐路径若为独立实例（涉数据迁移），实施前先报黑板请 PM 确认；调高 `max_connections` 路径可按本单直接实施。
2. **实施推荐路径，但切断/重启类操作一律在 11-15 09:50 D2 复判之后**：`max_connections` 须重启 postmaster 才能生效，独立实例须迁移/切换采集器与 Web 的连接——两类操作都会打断采集写入与 D2 判定窗（11-12/13/14 三日 15:00 桶），故 D2 之前只做评估与准备（写配置、备脚本、备回退），不动库、不重启采集器/Web/数据库容器。
3. **D2 之前只监不擅动**：每日巡检连接池占用（ESTABLISHED 数、占用方 PID）；若连接池在 D2 之前再次占满，只报黑板、不擅自重启任何进程，等用户处置。
4. **实施后验证**：采集器与 Web 在新配置下稳定在跑、sql_stat 持续续写、连接池不再能被 DB_Monitor 开发实例单方占满（以配置复核或受控验证为准，验证方法写进报告）。
