# DB-024：修复 DB-022 检测器实库缺陷

执行：GG

## 背景

- DB-022-补充实库补证报告已验收不通过（PM 采信，STATUS v1.45）：外网 4 库仅 PostgreSQL 16.13 全部 12/12 正常通过；DM8 15 项中 9 项 SQL 失效（6 项直接 error、3 项报错被吞成 ok），GBase 8a 10 项中 6 项异常＋1 项变量空行，MySQL 8.0.45 12 项中 5 项异常＋1 项变量空行；Oracle 分支 23 项未测·延后。
- DB-022 仍有条件通过：PG 分支已关闭（12/12 实库通过）；DM/GBase/MySQL 三分支不关闭，转入本单修复；Oracle 分支仍延至上线后内网复测。
- 缺陷明细见补证报告 `docs/pm/reports/DB-022-补充-实库补证-report-GG.md` §七（根因 A/B 与 DM/GBase/MySQL 方言失配）。

## 任务

1. **根因 A——DictCursor 与检测器取值不兼容**：`monitor/db_connector.py` 第 143 行对 mysql/gbase/tdsql 统一设 `cursorclass=pymysql.cursors.DictCursor`，而 `GenericDetector` 按元组下标 `r[0]/r[1]/row[1]` 或 `dict(zip(cols, r))` 取值，致 MySQL 上真实假阴性漏报（3 个锁定账号被吞成 0）、SPARSE-INDEX 10 行值错位成列名、PARAM-DEV 报 `KeyError: 1`。修法二选一：连接器改回元组游标，或检测器改按字典键取值；以不破坏其他调用方为准，改动面写进报告。
2. **根因 B——内层裸 `except` 吞错致假绿**：`GenericDetector` 内 11 处（DM 3、GBase 5、MySQL 3）SQL 报错被 `except Exception` 置空/置 0 后返回 `ok`。去掉静默吞错：异常须落 `error` 或 `degrade`，不得静默返回 `ok`/0/空结果；`detect_open_cursors` 的硬编码假值（"打开游标数 0（上限 1000）"）一并去掉。
3. **DM 方言 SQL 9 项**（按补证报告 §七.3 修正）：PWD-EXPIRE（`dba_users` 列为 `EXPIRY_DATE`）、PART-NEEDED（`dba_segments` 列为 `SEGMENT_NAME`）、PARAM-DEV（`V$PARAMETER` 列为 `NAME`、`VALUE`）、ARCH-GAP（DM8 无 `V$ARCHIVE_GAP`，参考 DB-009 的 `V$ARCH_STATUS`/`V$ARCH_FILE` 口径）、LOCK-WAIT 与 BLOCK-SESSION（`V$SESSIONS` 无 `BLOCKED`/`BLOCKER_SESS_ID`/`WAIT_TIME`，参考 DB-009 的 `V$LOCK`/`V$TRX` 关联口径）、OPEN-CURSOR（无 `V$OPEN_TABLES`）、TEMP-USAGE（无 `dba_temp_files`，实测 `V$TABLESPACE WHERE TYPE$=2` 可用）、UNDO-USAGE（无 `V$UNDO_SPACE`；且函数内部取到行后须更新 `pct_used`）。
4. **GBase 方言 SQL 6 项＋1 变量空行**（按 §七.4 修正）：USER-LOCKED 与 PWD-EXPIRE（GBase 8a 无 `mysql` 库，用户表为 `gbase.user` 且无 `account_locked`/`password_lifetime` 列）；LOCK-WAIT、BLOCK-SESSION、TEMP-USAGE（GBase 无 InnoDB，缺 `innodb_lock_waits`/`innodb_trx`/`innodb_temp_table_info`，改查 GBase 实际来源）；DEADLOCK-24H（`Innodb_deadlocks` 变量不存在，返回恒为 0——与能力边界对齐或明确记 `skip`）。
5. **MySQL 8.0 方言 SQL 2 项＋1 变量空行**（按 §七.5 修正）：LOCK-WAIT（8.0 已移除 `information_schema.innodb_lock_waits`，改查 `performance_schema.data_lock_waits`，实测 `cnt=0` 可用）；TEMP-USAGE（`innodb_temp_table_info` 仅含 `TABLE_ID, NAME, N_COLS, SPACE`，无 `allocated` 列）；DEADLOCK-24H（`Innodb_deadlocks` 状态变量在 8.0 不存在，改查 `information_schema.INNODB_METRICS` 的 `lock_deadlocks`）。
6. **容量预测观察**（§七.6）：CAP-7D/CAP-30D 样本计数须过滤 `status='UP'`（DM cid=9 的 1588 条中含缺驱动 DOWN 记录），并做实际容量斜率外推（或在报告中写明不做的原因）；`db_monitor` 本身不在 `DatabaseConfig` 中，纳管库与元数据库须区分。
7. **复测**：修复后在同一 4 个外网实库（宿主 DM8 cid=9、GBase 8a 127.0.0.1:5258、MySQL 8.0.45 13306 cid=19、PostgreSQL 16.13 db_monitor）逐项重跑，逐项留实测输出原文；Oracle 仍延后。
