### 3.3 容器与 gbase 健康检查假阴性（定性）

| 容器 | 状态 |
|---|---|
| db-aiops-timescaledb | Up About an hour (healthy)，起 08:05:57Z |
| db-aiops-mysql | Up 21 minutes (healthy) |
| db-aiops-redis / postgres / tdsql-sim / oracle / elasticsearch | 各 Up 20 minutes (healthy) |
| **db-aiops-gbase** | **Up 20 minutes (unhealthy)**，起 09:02:01Z，`failing_streak=85` |

gbase 的 `unhealthy` 是**假阴性，实例实际可用**：

1. 容器内 `/proc/net/tcp6` 实测监听 `00000000000000000000000000000000:148A`（**0x148A＝5258**，状态 0A＝LISTEN）；`/proc/net/tcp` 只有 Docker 内嵌 DNS（127.0.0.11:36217）—— 即服务监听在 **IPv6**，只看 tcp 表会误判「无监听」。
2. 容器日志实测含 `Starting GBase SUCCESS!` 与 `Express is ready for connections.`（09:02:01）。
3. 根因：healthcheck 为 `gbase -uroot -proot -e 'SELECT 1'`，而客户端在 **`/home/gbase/GBase/server/bin/gbase`**，只有 `source ~/.bashrc`（载 `.gbase_profile`）后才在 PATH —— 实测 `command -v gbase` 无输出、source 后返回该路径；healthcheck 未 source ⇒ 命令找不到 ⇒ exit 1 ⇒ 连续失败 85 次。
4. 影响面：任何以 `docker ps` 健康列为准的巡检会误判 GBase 不可用。**§15／§16 均未记此点** → 第六节订正 2。

**另**：宿主 `netstat` 在本机查不到容器发布端口的 LISTEN 行（Docker Desktop/WSL2 后端表现），**不能**用它反推「端口未开」；§15 恢复前的端口 closed 结论来自当时实测，两次口径不同、不构成矛盾。
