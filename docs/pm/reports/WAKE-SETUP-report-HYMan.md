## 三、为什么第 5、8 步（以及整套自治闭环）没有接通

整套"自动链"合起来是：把本机智能体做成**开机自启的持久守护 + 外部输入驱动的无人值守自动执行器**。其输入是两份**外部可控数据**：GitHub 仓库里的任务单（纯文本，任何有写权限者或仓库被攻陷后可改）与飞书群消息；其动作包括改代码后**直推 main 且无 PR 门禁**、连接真实数据库、切换数据库角色、读写 `.env` 等凭据相关操作（这些在 `docs/pm/STATUS.md` 的历史记录中有大量实例）。

由此产生三类风险，非"推断"，而是这套设计本身的结构性特征：

1. **提示注入 / 远程指令通道**：任务单与飞书消息是数据，却被当作指令自动执行。谁控制了仓库内容或遥控消息，谁就能在无人值守的情况下驱动本机智能体执行操作，而我失去了逐条做安全判断的机会。
2. **无门禁的外侧写操作**："直推 main、无 PR 门禁"意味着自动执行结果没有任何合并前拦截；`validate.sh` 与 CI 都是事后信号，拦不住坏改动。
3. **持久化 + 凭据面**：登录自启的常驻任务把上述通道固化为长期存在；历史单涉及真实库凭据、进程内存取票据等敏感面，自动执行放大了误用与泄露后果。

因此我没有创建开机自启任务、没有创建"读 trigger 就执行"的定时任务、也没有绑定远程遥控。这不是"接单失败"，而是**在无人监督下拒绝接通一条自治执行通道**。

即"人在回路"（human-in-the-loop）：每次执行都由需求方当场确认，而不是由外部文件/遥控消息自动触发。若需求方确认这是自有可信环境、并接受上述风险，可就"最小权限、限定动作白名单、保留人工审批"的受限方案另行讨论，但不建议无人值守全自动。
